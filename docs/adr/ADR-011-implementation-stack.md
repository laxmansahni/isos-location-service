# ADR-011: Implementation stack – C# on .NET 10 with ASP.NET Core controllers

| | |
|---|---|
| **Status** | Accepted (decided by the project owner, 2026-11-19; implementation started) |
| **Date** | 2026-11-19 |
| **Requirements** | NFR-01 to NFR-05, NFR-08 |

## Context

The service needs a language and web framework. The project owner decided to build it in .NET. The solution was created in Rider as an ASP.NET Core Web API (`ISOS.LocationService.sln`, project `src/ISOS.LocationService`, target `net10.0`).

## Decision drivers

- Fit with the existing .NET services and skills (the mobile middleware is .NET).
- Long-term support and security patches.
- An explicit, reviewable HTTP contract, since two separately released apps (Assistance App and Quantum) call it.
- Several endpoints share the same rules: policy check, tenant scoping and audit.

## Decision

1. **C# on .NET 10** (LTS). Confirm with Platform that .NET 10 is approved for their runtime and base images.
2. **ASP.NET Core Web API with controllers.** The template generated `AddControllers()`; the whole service stays on one style (no mixing with minimal APIs).
3. **OpenAPI** document generated by `Microsoft.AspNetCore.OpenApi`, published as the contract for both client teams.
4. **No authentication scheme in the template.** Authentication and authorisation are designed separately: Okta tokens for the Assistance App, and an open question for Quantum (HLD Q8).
5. **PostgreSQL access through Npgsql with hand-written SQL, and schema migrations as plain SQL scripts run by DbUp** (ADR-010). EF Core and Dapper were considered; the partitioned history table, `ON CONFLICT DO NOTHING`, partition creation and partition drop are PostgreSQL-specific SQL either way, so an ORM adds little for the first tables. Revisit if the query side (map, history, replay) grows many entity-shaped queries.
6. **Code organised by module** (ingestion, policy, query), each with its own controller and related code, in one deployable. A worker project is added for the purge job when it is built (HLD 4.2).

Solution layout: `ISOS.LocationService.sln` at the repository root, code under `src/`, tests under `tests/` when added.

## Options considered

| Option | Result |
|---|---|
| ASP.NET Core controllers | **Chosen.** Explicit structure for about ten endpoints sharing filters and policies; familiar to the .NET teams |
| ASP.NET Core minimal APIs | Also viable and the template default. Rejected only to keep one consistent style; endpoint groups would be needed to keep `Program.cs` small |
| .NET Native AOT | Rejected: limits reflection-based libraries and no startup benefit is needed |
| gRPC | Rejected: Quantum is a browser app and both clients use plain HTTPS/JSON |
| Another language or framework | Not considered further; the stack decision is .NET |

## Consequences

- Runtime and container choices (Docker, EKS or other) are still open with Platform (HLD Q9); the framework choice does not fix them.
- Contract tests between the service and each client are needed, since the clients release independently (LLD 8).
- Rider is the standard IDE; the `.idea/` folder and build output are not committed.

## Open items

- Platform confirms .NET 10 support and the hosting runtime (HLD Q9).
- Authentication for Quantum (HLD Q8).
- Whether the query side later warrants an ORM (EF Core or Dapper).
